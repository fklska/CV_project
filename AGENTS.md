# CV_project — восстановление сейсмических кубов

Студенческое задание: `inpainting` (внутренняя область пропусков) и `outpainting` (граничные полосы) куба сейсмических данных с помощью 2.5D U-Net.

## Структура
- `inpainting.ipynb` / `outpainting.ipynb` — рабочие ноутбуки, одинаковая структура блоков: окружение → данные (SHA-256 + проверка нулей) → модель → обучение → тестирование → инференс → сохранение артефактов.
- `0_seismic.ipynb`, `TEMPLATE_independent_work_result.ipynb`, `SeismicUtils.py`, `slides.md` — исходные материалы и шаблоны.
- `requirements.txt` — зависимости (torch, numpy, matplotlib, ipywidgets, tensorboard, jupyter, tqdm, mlflow).
- `inference/` — локальный просмотрщик восстановленных кубов (serve.py + index.html), см. «Inference viewer».

## Конвенции
- Ноутбуки — JSON c `indent=1`, `ensure_ascii=False`, `source` ячейки = массив по одной строке (со своим завершающим `\n`). Править через скрипт (json.load → правка `source` → json.dump в том же формате + завершающая `\n`), не править руками.
- Прогресс обучения — tqdm: внешняя полоса по эпохам со `set_postfix` (train всегда, val на эпохах валидации), вложенные полосы `tqdm(loader, desc="train"/"val", leave=False)`; print в блоке обучения нет.
- Оба ноутбука: matplotlib принудительно в бэкенде `Agg` — `plt.show()` в вычислительном окружении зависает; все визуализации (тестовые примеры, восстановленные срезы, история обучения) — статические PNG (`fig.savefig` + `display(Image(...))`); plotly и ipywidgets удалены из ноутбуков и `requirements.txt` (JS от `fig.show()` и виджеты `ipywidgets` в фронтенде не рендерятся — клетка с слайдером зависала в бесконечном выполнении). Вместо слайдера — статическая клетка `*-restored-slices`: сетка 4 среза × 3 панели → `*_restored_slices.png`; `show_restored_slice(N)` (объект `slice_panels` — общее построение панелей одного среза) осталась для ручного просмотра конкретного среза. Прогресс — классический `from tqdm import tqdm`.
- Общие настройки обучения: `NUM_WORKERS = 0` (воркеры DataLoader в вычислительном окружении зависали без ошибки), `VALIDATION_EVERY = 1`, `R_LOSS_WEIGHT = 0.5`. Потеря = `L1 + MSE + w_grad·∇L1 + w_HF·HFL1 + w_F·FFL + 0.5·(1 − R)`; HF-слагаемое — Sobel X/Y + Laplacian на масштабах 1, 1/2 и 1/4; FFL — focal frequency loss по амплитуде `rfft2((pred − target)·mask, norm="ortho")`: вес частоты `|Δ| / max|Δ|`, штраф `weight·|Δ|²` (float32 вне autocast, как HF). В обоих ноутбуках `FFL_WEIGHT = 0.05`, вес линейно растёт в течение `FFL_WARMUP_EPOCHS = 5` и логируется в TensorBoard/MLflow; на test применяется полный вес. Outpainting: `L1_WEIGHT = 1.0`, `GRAD_LOSS_WEIGHT = 0.3`, `HIGH_FREQ_LOSS_WEIGHT = 0.1`; для ablation: `GRAD_LOSS_WEIGHT = 0.0`, `RUN_NAME = "no-grad-l1"`.
- Inpainting: `BATCH_SIZE = 32`, `EPOCHS = 150`, `EARLY_STOPPING_PATIENCE = 24`, `L1_WEIGHT = 0.85`, `GRAD_LOSS_WEIGHT = 1.0`, `HIGH_FREQ_LOSS_WEIGHT = 0.5`, `FFL_WEIGHT = 0.05`, `RUN_NAME = "ffl-cosine"`; LR — 3 эпохи линейного warmup до `BASE_LR = 1e-3` + cosine-затухание до `MIN_LR = 1e-5` за `EPOCHS` (`LambdaLR`, функция `cosine_lr_lambda`), `scheduler.step()` без условий каждый эпох.
- Outpainting: `BATCH_SIZE = 16`, `EPOCHS = 75`, `EARLY_STOPPING_PATIENCE = 12`, `FFL_WEIGHT = 0.05`, `RUN_NAME = "ffl"`; `ReduceLROnPlateau(mode="max", factor=0.5, patience=4, min_lr=1e-5)`.
- Патчи: `inpainting.ipynb` — 368×176 (помещается во все `REGIONS`; верхняя вертикальная позиция фиксирована, для нижней есть 3), `outpainting.ipynb` — 368×256. В обоих ноутбуках bottleneck содержит свёртки с dilation 2 и 4.
- Метрика R в обоих ноутбуках — единый глобальный Пирсон по всем маскированным значениям эпохи (одна формула для train, val и test), а не среднее по батчам; накапливается на GPU через моменты (`new_r_moments`/`add_r_moments`/`r_from_moments`), синхронизация GPU→CPU один раз в конце эпохи. `correlation_r` остаётся для batch-R в потере и test-клетки.
- Аугментация только для train в обоих ноутбуках: положение патча, отражения, масштаб амплитуд `AMP_SCALE_RANGE = (0.9, 1.1)` и гауссов шум `NOISE_SIGMA = 0.05` генерируются заново при каждом обращении через RNG датасета; `TRAIN_SAMPLES_PER_CENTER`: inpainting = 6 (val = 8, test = 4), outpainting = 4 (val/test = 4), validation/test фиксированы seed 43/44. В `inpainting.ipynb` положение маски также рандомизируется внутри `REGIONS`; в `outpainting.ipynb` маска — фиксированные полосы шириной 24 сверху и снизу патча.
- MLflow-трекинг в обоих ноутбуках: константы в блоке окружения, импорт в `try/except` → флаг `MLFLOW_AVAILABLE` (нет клиента/сервера — ноутбук продолжает работать без треккинга); каждый запуск setup-клетки создаёт новый run (предыдущий активный завершается `end_run`), `log_params` включает `param_count` + теги `model/architecture`/`log_dir`, метрика `lr` логируется каждый эпох, на эпохах валидации `log_metric`; только в MLflow дополнительно логируются взвешенные вклады L1, MSE, R, gradient, high-frequency и FFL для train/validation (`train_*_loss`/`val_*_loss`) и средняя по батчам L2-норма градиентов `train_gradient_norm` после AMP-unscale (через `clip_grad_norm_` с бесконечным порогом, без клиппинга); TensorBoard-события пишутся в подпапку на запуск `runs/<task>/<timestamp>` и дублируют метрики MLflow: `Epoch`, `Learning rate`, `Loss/train`/`validation`/`test`, `R/train`/`validation`/`best_validation`/`test`, `Weights/FFL`; для test-метрик открывается отдельный `SummaryWriter` в том же `LOG_DIR`; в клетке тестов `test_r`/`test_loss` + `mlflow.pytorch.log_model` c `serialization_format="pickle"` (дефолтный в MLflow ≥3 формат pt2 требует TensorSpec-сигнатуру — тяжелее, чем надо; артефакт регистровый, инференс идёт через `torch.load` чекпоинта) + версия в Model Registry + `end_run`. URI `http://127.0.0.1:5000`, эксперименты `inpainting`/`outpainting`, модели `inpainting_unet`/`outpainting_unet`. Сервер: `docker compose up -d` в `C:\Dev\services\mlflow`; клиент `mlflow` в `requirements.txt` (wheel в `C:\Dev\offline_packages` отсутствует — для вычислительного окружения качать отдельно).
- Разбиение: `inpainting.ipynb` — доли `TRAIN_RATIO`/`VAL_RATIO`/`TEST_RATIO = 0.88/0.08/0.04`, `SPLIT_GAP = 4`, `SLICE_RANGE = (2, 578)`; `outpainting.ipynb` — фиксированные центры (train 2–321, val 326–395, test 400–457) с защитными зазорами.
- Куб в обоих ноутбуках предзагружен в оперативную память (`np.load(DATA_PATH)`) вместо mmap: копирование патчей в датасете быстрее.
- В блоке тестирования обоих ноутбуков первая клетка загружает модель `UNet25D().to(device)` из чекпоинта (`best_inpainting_unet.pt` / `best_outpainting_unet.pt`): метрики и примеры предсказаний считаются на лучшей по валидационному R модели, а не на последней эпохе обучения.
- Инференс обоих ноутбуков — однопроходный. `predict_region` строит вход из 5 кадров исходного куба и маски, выполняет один проход сети и возвращает предсказание всего среза. `restore_slice` заменяет предсказанием только область пропусков; визуализация (`slice_panels`/`show_restored_slice`) и сохранение куба используют одну и ту же функцию `restore_slice`.
- Детерминизм: `SEED=42` (random/np/torch/cuda). В `inpainting.ipynb` детерминизм сброшен ради скорости: `torch.backends.cudnn.benchmark = True` без `use_deterministic_algorithms` (разбег метрик между запусками ~1e-3); `outpainting.ipynb` остаётся детерминированным (`CUBLAS_WORKSPACE_CONFIG=:4096:8` + `use_deterministic_algorithms`).

## Inference viewer
- `inference/serve.py` — автономный HTTP-сервер (stdlib + numpy, без других зависимостей): `python inference/serve.py --port N` → `http://127.0.0.1:N` (пути закреплены к корню проекта, не зависят от cwd). Автоскан `output/*/<task>_cube_restored.npy` (manifest живой — новые кубы появляются после обновления страницы без перезапуска). В RAM одновременно один куб (новый высвобождает старый, загрузка ~1–3 с); эндпоинты: `/` (index.html, читается с диска на каждый запрос), `/manifest` (JSON `{"cubes": [...]}`: shape, коробки пропусков, missed axis), `/slice?sub&task&axis&i` (uint8-плоскость, квантование p1–p99 по известным значениям куба). В manifest, кроме восстановленных, всегда два исходных куба `input_seismic_data/{inpainting,outpainting}_cube_missed_data.npy` (метка `label: «исходный»`, те же boxes/missed axis); серверятся через тот же `/slice` (в RAM по-прежнему один куб, исходные и восстановленные вытесняют друг друга).
- `inference/index.html` — просмотрчик: селектор куба (подпапка + задача), селектор оси (по умолчанию «ось пропусков»: inpainting→0, outpainting→1), слайдер среза (при смене оси/куба позиция сбрасывается туда, где пропуски видны: 0, если 0 внутри области пропусков, иначе середина первого интервала пропусков по оси), одна панель «Результат» (крупно) + подписи размерностей осей (ось K · M); область пропусков обведена красным контуром, в исходных кубах поверх — полупрозрачная подложка + штриховка + подпись «нет данных» (ноль пропусков квантуется в чёрный и сливался с фоном, поэтому выделен явно); пиксели панели записываются как `plane[x*h + y]` (x — ось `dims[0]`, y — `dims[1]`): прямое плоское копирование `plane[p]` давало сдвинутый (sheared) срез при различном размере двух осей; в селекторе кубов два «исходных» из `input_seismic_data` (в них пропуски нулевые — сравнение с результатом). Области пропусков заданы жёстко в `serve.py` (`TASKS`): inpainting `[:, 368:581, 179:282]`, outpainting `[:, 0:24, :]` + `[:, 457:481, :]`.
- `inference/README.md` — как запускать.

## Запуск и проверка
- Ноутбуки требуют входной `.npy` из `input_seismic_data/` и torch; локально torch не установлен — ноутбуки исполняются в вычислительном окружении.
- Скрипты проверки JSON/синтаксиса ячеек пишутся во временные `tmp_*.py` и удаляются после проверки.
- В кубах пропуски хранятся как 0 (NaN нет), поэтому проверка односторонняя: «область пропусков заполнена нулями». Вне области есть естественные нули (inpainting: 1 в (451, 363, 437), outpainting: 73), поэтому строгое сравнение `cube == 0` с маской не используется.
