# CV_project — восстановление сейсмических кубов

Студенческое задание: `inpainting` (внутренняя область пропусков) и `outpainting` (граничные полосы) куба сейсмических данных с помощью 2.5D U-Net.

## Структура
- `inpainting.ipynb` / `outpainting.ipynb` — рабочие ноутбуки, одинаковая структура блоков: окружение → данные (SHA-256 + проверка нулей) → модель → обучение → тестирование → инференс → сохранение артефактов.
- `0_seismic.ipynb`, `TEMPLATE_independent_work_result.ipynb`, `SeismicUtils.py`, `slides.md` — исходные материалы и шаблоны.
- `requirements.txt` — зависимости (torch, numpy, matplotlib, ipywidgets, tensorboard, jupyter, tqdm, mlflow).

## Конвенции
- Ноутбуки — JSON c `indent=1`, `ensure_ascii=False`, `source` ячейки = массив по одной строке (со своим завершающим `\n`). Править через скрипт (json.load → правка `source` → json.dump в том же формате + завершающая `\n`), не править руками.
- Прогресс обучения — tqdm: внешняя полоса по эпохам со `set_postfix` (train всегда, val на эпохах валидации), вложенные полосы `tqdm(loader, desc="train"/"val", leave=False)`; print в блоке обучения нет.
- Оба ноутбука: matplotlib принудительно в бэкенде `Agg` — `plt.show()` в вычислительном окружении зависает; все визуализации (тестовые примеры, восстановленные срезы, история обучения) — статические PNG (`fig.savefig` + `display(Image(...))`), plotly удалён из ноутбуков и `requirements.txt` (JS от `fig.show()` в фронтенде не рендерится). Прогресс — классический `from tqdm import tqdm`: виджеты `tqdm.auto` в фронтенде вычислительного окружения не отображаются.
- Настройки обучения обоих ноутбуков: `BATCH_SIZE = 32` (6 Гб VRAM), `NUM_WORKERS = 0` (воркеры DataLoader в вычислительном окружении зависали без ошибки), `VALIDATION_EVERY = 1` — валидация/чекпоинт/ранняя остановка каждый эпох; `EPOCHS = 75`, `EARLY_STOPPING_PATIENCE = 12`, `ReduceLROnPlateau(patience=4, min_lr=1e-5)`, `L1_WEIGHT = 1.0`, `GRAD_LOSS_WEIGHT = 0.3`, `R_LOSS_WEIGHT = 0.1` (потеря = `L1 + MSE + 0.3·∇L1 + 0.1·(1 − R)`; градиентный член — L1 по первым разностям в маскированной области, добавлен для резкости вывода вместо «мыльного» усреднения L1/MSE).
- Метрика R в обоих ноутбуках — единый глобальный Пирсон по всем маскированным значениям эпохи (одна формула для train, val и test), а не среднее по батчам; накапливается на GPU через моменты (`new_r_moments`/`add_r_moments`/`r_from_moments`), синхронизация GPU→CPU один раз в конце эпохи. `correlation_r` остаётся для batch-R в потере и test-клетки.
- Аугментация только для train в обоих ноутбуках: отражения патчей + масштаб амплитуд `AMP_SCALE_RANGE = (0.9, 1.1)` + гауссов шум `NOISE_SIGMA = 0.05` в известные значения входа (шум детерминирован по образцу: `np.random.default_rng(index)`); `TRAIN_SAMPLES_PER_CENTER = 4` (val/test = 4). В `inpainting.ipynb` дополнительно рандомизируется положение маски внутри `REGIONS`; в `outpainting.ipynb` маска — фиксированные полосы шириной 24 сверху и снизу патча.
- MLflow-трекинг в обоих ноутбуках: константы в блоке окружения, импорт в `try/except` → флаг `MLFLOW_AVAILABLE` (нет клиента/сервера — ноутбук продолжает работать без треккинга); каждый запуск setup-клетки создаёт новый run (предыдущий активный завершается `end_run`), `log_params` включает `param_count` + теги `model/architecture`/`log_dir`, метрика `lr` логируется каждый эпох, на эпохах валидации `log_metric`; TensorBoard-события пишутся в подпапку на запуск `runs/<task>/<timestamp>`; в клетке тестов `test_r`/`test_loss` + `mlflow.pytorch.log_model` c `serialization_format="pickle"` (дефолтный в MLflow ≥3 формат pt2 требует TensorSpec-сигнатуру — тяжелее, чем надо; артефакт регистровый, инференс идёт через `torch.load` чекпоинта) + версия в Model Registry + `end_run`. URI `http://127.0.0.1:5000`, эксперименты `inpainting`/`outpainting`, модели `inpainting_unet`/`outpainting_unet`. Сервер: `docker compose up -d` в `C:\Dev\services\mlflow`; клиент `mlflow` в `requirements.txt` (wheel в `C:\Dev\offline_packages` отсутствует — для вычислительного окружения качать отдельно).
- Разбиение: `inpainting.ipynb` — доли `TRAIN_RATIO`/`VAL_RATIO`/`TEST_RATIO`, `SPLIT_GAP`, `SLICE_RANGE`; `outpainting.ipynb` — фиксированные центры (train 2–321, val 326–395, test 400–457) с защитными зазорами.
- Куб в обоих ноутбуках предзагружен в оперативную память (`np.load(DATA_PATH)`) вместо mmap: копирование патчей в датасете быстрее.
- В блоке тестирования обоих ноутбуков первая клетка загружает модель `UNet25D().to(device)` из чекпоинта (`best_inpainting_unet.pt` / `best_outpainting_unet.pt`): метрики и примеры предсказаний считаются на лучшей по валидационному R модели, а не на последней эпохе обучения.
- Детерминизм: `SEED=42` (random/np/torch/cuda). В `inpainting.ipynb` детерминизм сброшен ради скорости: `torch.backends.cudnn.benchmark = True` без `use_deterministic_algorithms` (разбег метрик между запусками ~1e-3); `outpainting.ipynb` остаётся детерминированным (`CUBLAS_WORKSPACE_CONFIG=:4096:8` + `use_deterministic_algorithms`).

## Запуск и проверка
- Ноутбуки требуют входной `.npy` из `input_seismic_data/` и torch; локально torch не установлен — ноутбуки исполняются в вычислительном окружении.
- Скрипты проверки JSON/синтаксиса ячеек пишутся во временные `tmp_*.py` и удаляются после проверки.
- В кубах пропуски хранятся как 0 (NaN нет), поэтому проверка односторонняя: «область пропусков заполнена нулями». Вне области есть естественные нули (inpainting: 1 в (451, 363, 437), outpainting: 73), поэтому строгое сравнение `cube == 0` с маской не используется.
