# CV_project — восстановление сейсмических кубов

Студенческое задание: `inpainting` (внутренняя область пропусков) и `outpainting` (граничные полосы) куба сейсмических данных с помощью 2.5D U-Net.

## Структура
- `inpainting.ipynb` / `outpainting.ipynb` — рабочие ноутбуки, одинаковая структура блоков: окружение → данные (SHA-256 + проверка нулей) → модель → обучение → тестирование → инференс → сохранение артефактов.
- `seismic_dataset.py` — константы геометрии патчей/масок, генераторы примеров и классы датасетов обоих задач; датасеты живут в модуле, а не в клетках (spawn-воркеры DataLoader не импортируют классы, определённые в Jupyter-клетках).
- `0_seismic.ipynb`, `TEMPLATE_independent_work_result.ipynb`, `SeismicUtils.py`, `slides.md` — исходные материалы и шаблоны.
- `requirements.txt` — зависимости (torch, numpy, matplotlib, tensorboard, jupyter, tqdm, mlflow).
- `whl/` — офлайн-копии всех нужных wheels (182 пакета, версии соответствуют `.venv`), для офлайн-установки в вычислительном окружении.
- `inference/` — локальный просмотрщик восстановленных кубов (serve.py + index.html), см. «Inference viewer».

## Конвенции
- Ноутбуки — JSON c `indent=1`, `ensure_ascii=False`, `source` ячейки = массив по одной строке (со своим завершающим `\n`). Править через скрипт (json.load → правка `source` → json.dump в том же формате + завершающая `\n`), не править руками.
- Прогресс обучения — tqdm: внешняя полоса по эпохам со `set_postfix` (train всегда, val на эпохах валидации), вложенные полосы `tqdm(loader, desc="train"/"val", leave=False)`; print в блоке обучения нет.
- Оба ноутбука: matplotlib принудительно в бэкенде `Agg` — `plt.show()` в вычислительном окружении зависает; все визуализации (тестовые примеры, восстановленные срезы, история обучения) — статические PNG (`fig.savefig` + `display(Image(...))`); plotly и ipywidgets удалены из ноутбуков и `requirements.txt` (JS от `fig.show()` и виджеты `ipywidgets` в фронтенде не рендерятся — клетка с слайдером зависала в бесконечном выполнении). Вместо слайдера — статическая клетка `*-restored-slices`: сетка 4 среза × 3 панели → `*_restored_slices.png`; `show_restored_slice(N)` (объект `slice_panels` — общее построение панелей одного среза) осталась для ручного просмотра конкретного среза. Прогресс — классический `from tqdm import tqdm`.
- Общие настройки обучения: `NUM_WORKERS = 0` + `persistent_workers = NUM_WORKERS > 0` (датасеты живут в модуле `seismic_dataset.py` и импортируются spawn-воркерами, но 4 воркера на Windows нестабильны: в первой val-эпохе при старте воркеров и пиклинге куба ~100 МБ через пайп вылетает `OSError [Errno 22]`, а после сбоя ломается весь val_loader — перезапуск цикла не помогает, до рестарта ядра; `NUM_WORKERS = 0` стабилен, потеря ~5 с на эпоху), `VALIDATION_EVERY = 1`, `R_LOSS_WEIGHT = 0.5`. AMP — нативный bf16: `AMP_DTYPE = torch.bfloat16`, `use_amp = device.type == "cuda" and torch.cuda.is_bf16_supported()`; `GradScaler`/масштабирование потерь удалены (bf16 не требует), на GPU без bf16 — чистый fp32. В циклах train/val/test нет `.item()` в теле цикла: `total_loss`/`component_totals`/`total_gradient_norm` накапливаются как GPU-тензоры, синхронизация GPU→CPU — один раз в конце эпохи; веса модели, оптимизатора и чекпоинты остаются fp32. Потеря = `L1 + MSE + w_grad·∇L1 + w_HF·HFL1 + w_F·FFL + 0.5·(1 − R)`; HF-слагаемое — Sobel X/Y + Laplacian на масштабах 1, 1/2 и 1/4; FFL — focal frequency loss по амплитуде `rfft2((pred − target)·mask, norm="ortho")`: вес частоты `|Δ| / max|Δ|`, штраф `weight·|Δ|²` (float32 вне autocast, как HF). В обоих ноутбуках `FFL_WEIGHT = 0.05`, вес линейно растёт в течение `FFL_WARMUP_EPOCHS = 5` и логируется в TensorBoard/MLflow; на test применяется полный вес. Outpainting: `L1_WEIGHT = 1.0`, `GRAD_LOSS_WEIGHT = 0.3`, `HIGH_FREQ_LOSS_WEIGHT = 0.1`; для ablation: `GRAD_LOSS_WEIGHT = 0.0`, `RUN_NAME = "no-grad-l1"`.
- Inpainting: `BATCH_SIZE = 24`, `EPOCHS = 100`, `EARLY_STOPPING_PATIENCE = 24`, `L1_WEIGHT = 0.85`, `GRAD_LOSS_WEIGHT = 0.75`, `HIGH_FREQ_LOSS_WEIGHT = 0.5`, `FFL_WEIGHT = 0.05`, `RUN_NAME = "ring-attn"`; LR — 3 эпохи линейного warmup до `BASE_LR = 2e-3` + cosine-затухание до `MIN_LR = 1e-5` за `EPOCHS` (`LambdaLR`, функция `cosine_lr_lambda`), `scheduler.step()` без условий каждый эпох.
- Outpainting: `BATCH_SIZE = 16`, `EPOCHS = 75`, `EARLY_STOPPING_PATIENCE = 12`, `FFL_WEIGHT = 0.05`, `RUN_NAME = "ffl"`; AdamW `lr = 2e-3` + `ReduceLROnPlateau(mode="max", factor=0.5, patience=4, min_lr=1e-5)`.
- Патчи: `inpainting.ipynb` — 368×176 (помещается во все `REGIONS`; верхняя вертикальная позиция фиксирована, для нижней есть 3), `outpainting.ipynb` — 368×256. В обоих ноутбуках bottleneck содержит свёртки с dilation 2 и 4. Только в `inpainting.ipynb` после финального декодера (перед 1×1 head) стоит dilated refinement head — класс `DilatedRefiner`: два блока 3×3 (dilation 2 и 4, `bias=False`) + `GroupNorm` + `GELU` на 32 каналах, без изменения размерности; уточняет центр маски по крайним известным пикселям. Между третьей и четвёртой ступенями декодера (64 канала, 192×88) в `inpainting.ipynb` стоит ring-attention блок `RingAttention`: query — по пикселям внутри маски, key/value — только из кольца известных пикселей в `ring_width = 4` (макс-pooling mask-канала из `F.max_pool2d(mask, 2, 2)`), 4 головы по 16 каналов; выходная проекция `nn.Linear` с нулевой инициализацией, поэтому на старте обучения блок — identity; обновление записывается только в пиксели маски (в-плейс `upd[:, idx]`), известные пиксели не изменяются; буфер `upd` создаётся в dtype выхода `out_proj` (`torch.zeros(c, hw, dtype=src.dtype)`), иначе под AMP-bf16 `index_put` падает: выход декодера после `GroupNorm` остаётся fp32, а `qkv`/`out_proj` считаются в bf16; +16 384 параметра (qkv 64×192 + out_proj 64×64).
- Метрика R в обоих ноутбуках — единый глобальный Пирсон по всем маскированным значениям эпохи (одна формула для train, val и test), а не среднее по батчам; накапливается на GPU через моменты (`new_r_moments`/`add_r_moments`/`r_from_moments`), синхронизация GPU→CPU один раз в конце эпохи. `correlation_r` остаётся для batch-R в потере и test-клетки.
- Аугментация только для train в обоих ноутбуках: положение патча, отражения, масштаб амплитуд `AMP_SCALE_RANGE = (0.9, 1.1)` и гауссов шум `NOISE_SIGMA = 0.05` генерируются заново при каждом обращении через RNG датасета; `TRAIN_SAMPLES_PER_CENTER`: inpainting = 6 (val = 8, test = 4), outpainting = 4 (val/test = 4), validation/test фиксированы seed 43/44. В `inpainting.ipynb` положение маски также рандомизируется внутри `REGIONS`; в `outpainting.ipynb` маска — фиксированные полосы шириной 24 сверху и снизу патча.
- MLflow-трекинг в обоих ноутбуках: константы в блоке окружения, импорт в `try/except` → флаг `MLFLOW_AVAILABLE` (нет клиента/сервера — ноутбук продолжает работать без треккинга); каждый запуск setup-клетки создаёт новый run (предыдущий активный завершается `end_run`), `log_params` включает `param_count` + теги `model/architecture`/`log_dir`, метрика `lr` логируется каждый эпох, на эпохах валидации `log_metric`; только в MLflow дополнительно логируются взвешенные вклады L1, MSE, R, gradient, high-frequency и FFL для train/validation (`train_*_loss`/`val_*_loss`) и средняя по батчам L2-норма градиентов `train_gradient_norm` по fp32-градиентам (через `clip_grad_norm_` с бесконечным порогом, без клиппинга; `GradScaler` отсутствует — bf16); TensorBoard-события пишутся в подпапку на запуск `runs/<task>/<timestamp>` и дублируют метрики MLflow: `Epoch`, `Learning rate`, `Loss/train`/`validation`/`test`, `R/train`/`validation`/`best_validation`/`test`, `Weights/FFL`; для test-метрик открывается отдельный `SummaryWriter` в том же `LOG_DIR`; в клетке тестов `test_r`/`test_loss` + `mlflow.pytorch.log_model` c `serialization_format="pickle"` (дефолтный в MLflow ≥3 формат pt2 требует TensorSpec-сигнатуру — тяжелее, чем надо; артефакт регистровый, инференс идёт через `torch.load` чекпоинта) + версия в Model Registry + `end_run`. URI `http://127.0.0.1:5000`, эксперименты `inpainting`/`outpainting`, модели `inpainting_unet`/`outpainting_unet`. Сервер: `docker compose up -d` в `C:\Dev\services\mlflow`; клиент `mlflow` в `requirements.txt` (wheels в `C:\Dev\offline_packages` и в `whl/`).
- Разбиение: `inpainting.ipynb` — доли `TRAIN_RATIO`/`VAL_RATIO`/`TEST_RATIO = 0.88/0.08/0.04`, `SPLIT_GAP = 4`, `SLICE_RANGE = (2, 578)`; `outpainting.ipynb` — фиксированные центры (train 2–321, val 326–395, test 400–457) с защитными зазорами.
- Куб в обоих ноутбуках предзагружен в оперативную память (`np.load(DATA_PATH)`) вместо mmap: копирование патчей в датасете быстрее.
- В блоке тестирования обоих ноутбуков первая клетка загружает модель `UNet25D().to(device)` из чекпоинта (`best_inpainting_unet.pt` / `best_outpainting_unet.pt`): метрики и примеры предсказаний считаются на лучшей по валидационному R модели, а не на последней эпохе обучения; на всей тестовой маске считаются `test_loss` и глобальный `test_r` (TensorBoard `Loss/test`/`R/test`, MLflow `test_loss`/`test_r`).
- Инференс обоих ноутбуков — однопроходный: все пропущенные значения кодируются нулём и mask=1, как в обучении, а в куб записывается весь результат сети по маске пропусков. `predict_frames`/`predict_region`: окно 5 кадров `index±2` через `np.clip` — несуществующие контекстные кадры на срезах 0, 1 и двух последних дублируют ближайший реальный кадр вместо нулей; каждый срез восстанавливается независимо, контекст — из исходного куба. Блок сохранения — один проход по всем срезам (tqdm `inference`); `restore_slice` (визуализация `slice_panels`/`show_restored_slice`) — тот же однопроходный расчёт.
- Детерминизм: `SEED=42` (random/np/torch/cuda). Оба ноутбука недетерминированы: `torch.backends.cudnn.benchmark = True` без `use_deterministic_algorithms` (разбег метрик между запусками ~1e-3); детерминизм `outpainting.ipynb` (`CUBLAS_WORKSPACE_CONFIG=:4096:8` + `use_deterministic_algorithms`) снят.

## Inference viewer
- `inference/serve.py` — автономный HTTP-сервер (stdlib + numpy, без других зависимостей): `python inference/serve.py --port N` → `http://127.0.0.1:N` (пути закреплены к корню проекта, не зависят от cwd). Автоскан `output/*/<task>_cube_restored.npy` (manifest живой — новые кубы появляются после обновления страницы без перезапуска). В RAM одновременно один куб (новый высвобождает старый, загрузка ~1–3 с); эндпоинты: `/` (index.html, читается с диска на каждый запрос), `/manifest` (JSON `{"cubes": [...]}`: shape, коробки пропусков, missed axis), `/slice?sub&task&axis&i` (uint8-плоскость, квантование p1–p99 по известным значениям куба). В manifest, кроме восстановленных, всегда два исходных куба `input_seismic_data/{inpainting,outpainting}_cube_missed_data.npy` (метка `label: «исходный»`, те же boxes/missed axis); серверятся через тот же `/slice` (в RAM по-прежнему один куб, исходные и восстановленные вытесняют друг друга).
- `inference/index.html` — просмотрчик: селектор куба (подпапка + задача), селектор оси (по умолчанию «ось пропусков»: inpainting→0, outpainting→1), слайдер среза (при смене оси/куба позиция сбрасывается туда, где пропуски видны: 0, если 0 внутри области пропусков, иначе середина первого интервала пропусков по оси), одна панель «Результат» (крупно) + подписи размерностей осей (ось K · M); область пропусков обведена красным контуром, в исходных кубах поверх — полупрозрачная подложка + штриховка + подпись «нет данных» (ноль пропусков квантуется в чёрный и сливался с фоном, поэтому выделен явно); пиксели панели записываются как `plane[x*h + y]` (x — ось `dims[0]`, y — `dims[1]`): прямое плоское копирование `plane[p]` давало сдвинутый (sheared) срез при различном размере двух осей; в селекторе кубов два «исходных» из `input_seismic_data` (в них пропуски нулевые — сравнение с результатом). Области пропусков заданы жёстко в `serve.py` (`TASKS`): inpainting `[:, 368:581, 179:282]`, outpainting `[:, 0:24, :]` + `[:, 457:481, :]`.
- `inference/README.md` — как запускать.

## Запуск и проверка
- Ноутбуки требуют входной `.npy` из `input_seismic_data/` и torch; вычислительное окружение — проект: `.venv` с torch 2.15.0+cu134 (CUDA, bf16), `python = .venv\Scripts\python.exe`.
- Скрипты проверки JSON/синтаксиса ячеек пишутся во временные `tmp_*.py` и удаляются после проверки.
- В кубах пропуски хранятся как 0 (NaN нет), поэтому проверка односторонняя: «область пропусков заполнена нулями». Вне области есть естественные нули (inpainting: 1 в (451, 363, 437), outpainting: 73), поэтому строгое сравнение `cube == 0` с маской не используется.
- `real_mask` в обоих ноутбуках строится in-place: 3D `np.zeros(cube.shape, dtype=bool)` — inpainting `[:, 368:581, 179:282]`, outpainting полосы `0:24` и `457:481`; маски из `.npy` не читаются. Геометрический кросс-чек в клетке инференса не зависит от формы `real_mask` (3D/4D): `mask_0 = real_mask[0, :, :, 0] if real_mask.ndim == 4 else real_mask[0]`.
